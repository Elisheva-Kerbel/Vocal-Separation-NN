# DEC-0005 — DB base, sync SQLAlchemy session, and Alembic migration determinism

Status: **Approved for P2-001 planning / pending Nadav implementation authorization.**
Not an implementation authorization. Not production-approved. No public users.

Phase: 2 (Backend Domain + DB Skeleton) · Package: PKG-P2 · Recorded by: P2-000 readiness fixes
Relates to: `DEC-0002` (minimal code), `DEC-0003` (private storage only), `DEC-0004` (local model prototype), `docs/coding-rules.md`
Baseline: `stemspace-dev-pack-v0.1/phases/PHASE-02-backend-domain-db-skeleton.md`, `stemspace-dev-pack-v0.1/packages/PKG-P2-backend-domain-db-skeleton.md`, `stemspace-dev-pack-v0.1/tasks/phase-2/TASK-P2-001-db-base-and-alembic.md`

> This record documents **approved planning decisions** so that P2-001 can later be implemented
> without the code agent inventing DB architecture. It authorizes **no** code, **no** dependency
> installation, **no** migration and **no** database connection by itself. P2-001 begins only after
> Nadav reviews this P2-000 result and issues an explicit implementation authorization (see §12).

## 1. Decision

Fix the DB foundation contract for Phase 2: **PostgreSQL + synchronous SQLAlchemy + Alembic over
the psycopg3 sync driver**, with a `DeclarativeBase` base class, a shared `MetaData` carrying an
explicit **naming convention** so migrations are deterministic, and the database URL sourced
**only** through `backend/app/config.py` as a secret value.

This closes the architecture gaps that caused the Phase 2 readiness gate to report BLOCKED.

## 2. Status

**Approved for P2-001 planning / pending Nadav implementation authorization.**

The stack, session style, base style, naming convention, config path, dependency set, security
rules and test contract below are **decided**. Implementing them is a separate, later step.

## 3. Stack

- **PostgreSQL** — the only database. Local Compose Postgres only; **no production DB**.
- **SQLAlchemy — sync.** Version range `>=2.0,<3.0`.
- **Alembic** — the only migration tool. Version range `>=1.13,<2.0`.
- **psycopg3 sync driver** — `psycopg[binary]`, version range `>=3.1,<4.0`.
- **Pydantic remains the schema layer, not the DB layer.** DB models are never returned to clients;
  Pydantic schemas are the external contract (see `DEC-0003`, PKG-P2 "DB model is not API schema").

The URL scheme is `postgresql+psycopg://…`, matching the psycopg3 sync driver and the existing
`DATABASE_URL` placeholder already present in `.env.example`. Do not switch schemes.

## 4. Session decision

- Use a **sync `Session` / `sessionmaker`**.
- **No async SQLAlchemy in P2-001** — no `async_sessionmaker`, no `AsyncSession`, no `asyncpg`.
- **DB imports must not open connections at import time.** Importing `app.db` must construct no
  engine connection, run no query and reach no network. Engine creation is lazy; connecting happens
  only when a session is actually used. This protects the Phase 0 `/health` boundary and keeps the
  test suite runnable without a live database.
- No session-per-request wiring, dependency injection or service layer in P2-001 — there are no
  routes to serve (see §11).

**Rationale.** The MVP flow is not I/O-bound in a way that justifies async, and async would leak
into every downstream P3–P8 service. Sync is the smaller correct choice per `DEC-0002`. Revisiting
this later requires a new decision record, not an implementer's judgement call.

## 5. Base style

- Use **`DeclarativeBase`** (SQLAlchemy 2.x style), not the legacy `declarative_base()`.
- A **single shared `MetaData`** carrying the naming convention in §6, attached to the base.
- **Avoid an overbuilt mixin hierarchy.** Do not add ID/timestamp/audit mixins, abstract base
  entities or generic repository layers in P2-001. If a shared timestamp mixin proves genuinely
  necessary when models are designed, it is introduced then — with justification — not pre-built now
  (`DEC-0002`, minimal-code policy §"Not allowed in early phases").
- P2-001 delivers the **base and metadata only**. It defines **no entities** (see §11).

## 6. Naming convention

Migrations must be **deterministic**: constraint and index names are decided by this convention,
never auto-generated by the database backend. The shared `MetaData` must carry exactly:

| Key  | Pattern |
|------|---------|
| `ix` | `ix_%(column_0_label)s` |
| `uq` | `uq_%(table_name)s_%(column_0_name)s` |
| `ck` | `ck_%(table_name)s_%(constraint_name)s` |
| `fk` | `fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s` |
| `pk` | `pk_%(table_name)s` |

Requirements:

- The convention is attached to the **single shared `MetaData`** used by the base and by Alembic's
  `target_metadata`, so autogenerate and runtime agree.
- Alembic's `env.py` must reference that same metadata. A convention applied to only one side
  produces migrations that drift.
- **No backend-generated random constraint names.** A constraint whose name depends on the server
  cannot be reliably referenced by a later `downgrade()` or by a future ALTER.

**Rationale.** PKG-P2 Operational Readiness requires deterministic migrations. Without a naming
convention, PostgreSQL assigns constraint names, autogenerate emits unstable diffs, and downgrade
paths break — which would stale the downstream P3/P4 evidence PKG-P2 warns about.

## 7. DB URL / config decision

- The future P2-001 implementation **must extend `backend/app/config.py`** with a `database_url`
  field, following the existing `Settings` dataclass pattern.
- **Do not read `DATABASE_URL` directly in DB modules.** `app/db/` consumes config through
  `config.py`; scattered `os.getenv("DATABASE_URL")` calls are not permitted. One config source.
- `database_url` is a **secret**: it must be **repr-hidden** (`field(repr=False)`, matching how
  `s3_access_key_id` / `s3_secret_access_key` are already protected), never logged, never returned
  from any endpoint, and never included in metrics or health output.
- **A missing or empty DB URL must fail safely and visibly** — a clear, actionable error, not a
  silent fallback, not a default connection string, and not a hidden config error.
- **Error messages must not echo the DB URL or password.** `DATABASE_URL` must not be logged or
  echoed — not in exception text, not in Alembic log output, not in test failure output, not in
  tracebacks. Report *that* the URL is missing/invalid, never its value.

**Rationale.** `DATABASE_URL` embeds a password. `config.py` already solves this exact problem for
the `S3_*` credentials; reproducing the protection is cheaper than re-learning it after a leak.

## 8. Dependency decision

- The future P2-001 **may edit `backend/requirements.txt`** — its write scope is widened for this
  purpose (this was the write-scope gap that blocked the readiness gate).
- **Approved dependency set for P2-001, and nothing else:**
  - `sqlalchemy>=2.0,<3.0`
  - `alembic>=1.13,<2.0`
  - `psycopg[binary]>=3.1,<4.0`
- Version ranges follow the existing `requirements.txt` style (lower bound + major-version ceiling).
- **No `redis`, `celery`, `boto3`, `minio`, storage-client or queue dependencies in P2-001.** Those
  belong to their own approved phases and must not be pulled forward.
- No dependency is installed by this record. Installation happens only inside an authorized P2-001.
- `psycopg[binary]` is chosen so the local Compose image needs no build toolchain.

**Build-environment note (generic).** Adding these dependencies invalidates the cached pip layer in
`backend/Dockerfile`, so the next backend image build performs a **real dependency download**. If
Docker builds run behind a **TLS-intercepting proxy** (a corporate TLS proxy), that fetch fails
unless container CA trust is configured **outside the repository**. Keep TLS verification on; do not
commit TLS-bypass flags, private certificates, CA paths or provider-specific proxy configuration
(`docs/coding-rules.md` §5). Resolve this before P2-001 evidence is expected, or the build — not the
code — will be what fails.

## 9. Security decisions

These are binding on Phase 2 and every later phase that touches the data model.

- **No checkpoint/model/local filesystem paths in DB.** No column, default, comment, seed value or
  migration may store a checkpoint path, model path, weights filename or any operator-machine
  filesystem path.
- **No `LOCAL_MODEL_ROOT` value in DB.** It stays environment-only and out-of-band per `DEC-0004`.
  It is not persisted, not migrated, not seeded and not serialized.
- **No signed URL string in DB.** Signed URLs are short-lived credentials, never persisted
  (`DEC-0003`, `06-security-permissions-and-secrets.md`).
- **`SignedUrlGrant` stores audit/grant metadata only** — who was granted access, to what resource,
  when, and when it expired — and **never the signed URL string** itself. This resolves the apparent
  conflict between the `SignedUrlGrant` entity and the "signed URLs are not stored in DB" rule: the
  grant is an audit fact; the URL is a secret.
- **No audio bytes in DB.** Audio lives in private object storage; the database holds metadata only.
- **No public storage URLs.** No public bucket, no public object URL, no permanent file URL.
- **`storage_key` is internal only** and **must not be exposed** in client/API schemas. It may exist
  on internal DB/domain models when a later phase actually needs it; it never crosses the API
  boundary (`R-004`, PKG-P2 contract test, `DEC-0003`).
- **Clients never supply checkpoint identifiers.** Checkpoint selection stays server-side; a client
  sends at most a logical `modelTier` (`AGENT.md`, `DEC-0004` §5). Nothing in Phase 2 accepts client
  input at all.

### Canonical phrasing

These are the exact rules, stated plainly so they can be searched, quoted and audited verbatim:

- no audio bytes in DB
- no checkpoint/model/local filesystem paths in DB
- no LOCAL_MODEL_ROOT value in DB
- no signed URL string in DB
- storage_key must not be exposed in client/API schemas
- DATABASE_URL must not be logged or echoed
- no public bucket URLs and no public object URLs

## 10. Test contract

The future P2-001 must satisfy **all** of the following. This is the definition of done; the vague
"migration scaffold test" from the source task is replaced by this explicit list.

1. **Alembic config/env imports and loads** — `alembic.ini` and `alembic/env.py` resolve and import
   cleanly, without requiring a live database.
2. **DB URL is read through `config.py`** — not via a direct `os.getenv` in a DB module.
3. **Missing DB URL fails safely** — a clear error, **and the assertion proves the message does not
   echo the URL or password**.
4. **Importing `app.db` opens no DB connection** — no engine connection, no query, no network at
   import time.
5. **The naming convention exists and is deterministic** — the shared `MetaData` carries exactly the
   §6 keys, and Alembic's `target_metadata` is that same metadata object.
6. **Dependencies import** — `sqlalchemy`, `alembic` and `psycopg` import successfully.
7. **No production DB config** — no production host, no production credentials, no non-local default
   connection target anywhere in the committed configuration.
8. **Phase 0/1 regression tests still pass** — `/health`, config, worker startup, and the AI boundary
   lazy-import test (which proves `ai/*` pulls no heavy runtime deps) are unaffected by the DB
   dependencies landing.

Tests live under the repo's existing pytest layout (`backend/tests/`), matching current style.
A migration actually run against local Compose Postgres is **manual verification**, permitted only
when explicitly authorized — it is not required for the automated contract above.

## 11. Out of scope

P2-001 delivers the DB base, session config, Alembic scaffold and the §10 tests — nothing else.
Explicitly **not** in scope:

- **DB models/entities beyond the base/migration scaffold** — no `User`, `Song`, `AudioFile`,
  `SeparationJob` or any other entity (those are P2-002, and remain blocked on the state-enum and
  field decisions the readiness gate flagged).
- API routes (the existing `/health` is the only endpoint).
- Upload flow; queue processing; Redis; Celery.
- Storage client; MinIO/S3 access; signed URL generation.
- AI integration of any kind.
- Frontend changes; worker behavior changes.
- Production migrations; production DB config.
- **Auto-running migrations at app or container startup** — migrations are run deliberately, never
  implicitly on boot (PKG-P2 Operational Readiness).
- Auth, billing, admin, public library, resumable upload, extra stems beyond Vocals + Background.

## 12. Authorization boundary

- **P2-000** — this record and the Phase 2 readiness doc fixes. *(Currently authorized.)*
- **P2-001** — DB base and Alembic implementation. **Only after** Nadav reviews this P2-000 result

- **P2-002 onward** — remain blocked. P2-002 additionally requires the entity field definitions and

## Rationale

The Phase 2 readiness gate reported BLOCKED because P2-001 asked the code agent to pick a session
style, invent a constraint-naming approach, decide where the DB URL is read, and satisfy acceptance
criteria that its own write scope made unreachable — while `docs/coding-rules.md` §9 forbids the
agent from making architecture decisions or expanding scope. Deciding those points here, in an
authority-owned record, converts P2-001 from "guess and hope review catches it" into a mechanical,
verifiable task. Fixing the shared data foundation before it is written is far cheaper than
migrating away from it once P3–P8 depend on it.
